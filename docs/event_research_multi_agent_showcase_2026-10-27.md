# 多 Agent 能力展示与面试演示

更新日期：2026-10-27。当前项目展示的是**角色分工与编排能力**，不以单 Agent 准确率比较作为交付条件。早期对照实验和原始结果保留在仓库，供追溯，不作为演示结论。

## 实际分工

| 角色或组件 | 输入 | 职责与交接 |
| --- | --- | --- |
| 规划角色 | 用户问题、公司、日期窗口、工具白名单 | 生成带依赖的任务图及停止条件；编排器校验工具和日期，调度无依赖的检索任务并行执行。见 `app/agents/event_orchestrator.py`。 |
| 取证任务 | 规划节点 | 只读查询已保存的公告、新闻、财务和行情资料；返回来源、片段和执行轨迹，失败时保留已取得的证据。 |
| 事件提取角色 | 已取得的资料与原文 | 提取事件、日期、主张和引文，生成可追溯图谱并记录冲突。见 `app/agents/event_graph_builder.py`。 |
| 假设选择角色 | 用户问题、事件图谱 | 最多选择三个结构化解释方向和图谱主张 ID，不直接输出对外事实句。见 `app/agents/typed_hypothesis.py`。 |
| 反方核验角色 | 候选解释、已保存资料 | 检索反例，标记时序、冲突、来源依赖和其他解释；核验失败时降级。见 `app/agents/hypothesis_debate.py`。 |
| 程序质量门与报告 | 图谱、候选和核验结果 | 核对引用、日期、来源与费用边界，生成保守公开文字；证据卡把原文与未验证的支持关系分开。见 `app/reporting/event_report.py`。 |

这些角色使用同一已配置模型的不同提示与结构化契约，配合程序编排和只读工具；它们不是多个独立训练的模型，也不是无限自主运行的 Agent。无依赖的取证任务并行，事件提取、假设和反方按证据依赖先后执行。后台运行是单进程任务，不是分布式队列。

## 三分钟演示

1. 运行 `\.venv\Scripts\python.exe scripts/start_event_demo.py`，打开 `/research`，选择一家公司。说明这是**只读历史回放**，不会产生模型费用。
2. 展开事件时间线和原文抽屉，展示发生日、资料发布日期、逐字引文和冲突标记。强调图谱中的提取结果与原文分开显示。
3. 展开候选解释的证据卡与反方记录，指出“模型选作支持”并不等于解释成立，程序会在证据不足时给出保守结论。
4. 展示研究阶段、停止原因与费用边界。历史演示没有保存当时的完整规划轨迹，不能把静态回放说成现场运行了规划 Agent；任务图及并行调度可结合 `app/agents/event_orchestrator.py` 讲解，配置模型和来源库后的新研究运行才记录完整规划轨迹。

面试时可以解释三个设计决定：为什么任务图要有依赖和工具白名单；为什么引用可定位仍要把解释关系标为未验证；为什么反方核验失败时保留部分结果并停止，而不是补造完整结论。这些都能展示多 Agent 工作流设计，不需要宣称它优于单 Agent。

## 可用于简历的表述

> 基于 Python、FastAPI、SQLite 和 React 构建多 Agent 企业事件研究原型：设计带依赖的模型任务规划、白名单工具并行取证、事件证据图谱、结构化假设选择与反方核验；持久化执行轨迹和原文证据卡，并通过日期、引用、费用约束及失败降级控制输出。

不要写“已证明多 Agent 更准确”“已验证研究准确率”或“已证明股价因果”。
